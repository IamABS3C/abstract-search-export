# Abstract Search & Export: start here

This tool exports every event that matches a search in your Abstract tenant to a file on your computer, with a count that proves nothing was missed. You can build the search with filters, write it in KQL, or describe it in plain English. It reads from your tenant; the only things it can change there are fieldsets and saved views, and only after it shows you exactly what will change and you confirm.

> [!IMPORTANT]
> **What this tool does, and what it does not do**
>
> - **Use Abstract** for searching and investigating day to day. **Use this tool** when you need every matching event in one file, a range that reaches into the archive in one go, a count proved against Abstract's own total, the same export every day, an AI assistant that runs searches for you, or saved views and fieldsets kept as files.
> - **It does not delete, mask, redact or stop the collection of any data in Abstract.** Every export makes a new copy of your data outside Abstract (see [Where copies of your data end up](#where-copies-of-your-data-end-up)). To stop storing or to mask personal data, use Abstract's masking and retention settings, or ask your Abstract contact.
> - **It changes only fieldsets and saved views**, and only after a review you confirm.

### Before you start

- **A computer** with Python 3.8 or newer (Part 1 checks this), and access to `https://api.abstractsecurity.app`. On a company network you may need your proxy and certificate settings (see [Settings](#settings)).
- **Your vendor account ID and an API key** with the permissions in [step S2](#step-s2-get-your-vendor-account-id-and-api-key).
- **Comfort with a terminal**, or someone nearby who has it. The browser app needs one command to start.
- **Times are in UTC.** Every time the tool asks for or shows is UTC; the app also shows your own time zone next to it.
- **For the command line and schedules:** knowing how to set an environment variable, and a password manager or key vault with its command-line tool signed in.
- **For KQL:** reading a basic KQL search helps, but the builder and plain English need none.

## Part 1: Set up once

### Step S1: Check you have Python

The tool needs Python 3.8 or newer. Nothing else needs installing.

| System | What to do |
|---|---|
| **Mac** | Open **Terminal** (Applications, then Utilities), type `python3 --version` and press Enter. `Python 3.8` or higher means you are ready. | **Windows** | Open **PowerShell** (Start menu, type `powershell`) and type `py --version`. If it is not found, install Python from [python.org](https://www.python.org/downloads/) and tick **Add python.exe to PATH** on the first screen of the installer. |
| **Linux** | Open a terminal and type `python3 --version`. If it is missing, install it: `sudo apt install python3` (Ubuntu, Debian) or `sudo dnf install python3` (Fedora, RHEL). |

### Step S2: Get your vendor account ID and API key

Ask your Abstract administrator for your **vendor account ID** and an **API key**. Say what you will use it for, because each task needs its own permission. The names below are the ones Abstract gives these permissions.

| To do this | The key needs |
|---|---|
| Search and export recent data | **Read and Query Events** (`events.events.query`) and **Read Views** (`views.views.read`) |
| See the list of datasets | **Read Integration Configurations** (`integrations.configurations.read`) |
| Export data older than about 31 days (the archive) | Permission to run archive searches. When the key does not have it, `capabilities` shows the archive as not available and an export reports **Partial** (see [exit codes](#exit-codes)). |
| Save, change or delete saved views | **Write Views** (`views.views.write`) |
| Save, change or delete fieldsets | Permission to change fieldsets. Without it, Abstract refuses the change (HTTP 403) and nothing happens. |
| Plain English, where Abstract's assistant writes the KQL | **Use AI** (`ai.core.use`) |

Ask for **two keys** if you will change things in Abstract: a read-only key for exports and schedules, and a separate key with write permission that you use only when you mean to change views or fieldsets.

> [!CAUTION]
> Keep the key private. Never paste it into an email, chat, ticket or file. The tool never saves it and never shows it: on screen it is always `********`.

### Step B3: Pick the data

![The search panel: dataset, filters, time range and fields](docs/screenshots/web-02-build.png)

1. **Dataset:** start typing the name of the source you want, such as your firewall, and pick it from the list.
2. **Filters** (optional): choose **+ Add filter** to narrow it down, for example to one user or one IP address. Pick the field, then how it should match: *is one of*, *contains*, *does not contain*, *starts with*, *has the word*, a pattern, a number range, a subnet and more. Text ignores upper and lower case unless you tick **Match case**. With more than one filter, choose whether every filter or at least one must match.

> [!NOTE]
> A "not" filter, such as *does not contain*, leaves out events where the field is empty, as Abstract's search does. Tick **or has no value** on the filter to keep them.

### Step B4: Pick the time

Choose how far back to go, such as the last 24 hours or the last 7 days. For exact dates, choose **Custom range (UTC)**, then pick the start and end, or a quick range: **Today**, **Yesterday**, **Last 7 days**, **Last 30 days** or **Last month**. The line under each picker shows the same moment in your own time zone. You can also type a time, such as `2026-10-05T10:00:00Z`.

![Custom range: the date pickers and the quick ranges](docs/screenshots/web-15-time-and-estimate.png)

> [!NOTE]
> **Recent data and the archive.** Events from about the last 31 days are recent data and export quickly. Anything older is read from the archive by an **archive job**, which takes minutes for a day of range, or up to about an hour for a month. You can go back as far as your tenant keeps archived data. Your key needs permission to run archive searches (step S2).

### Step B5: Pick the fields

Choose which fields end up in the file:

- **Everything, every ACS and `ext` field:** tick **Every field of every event**. In NDJSON each event is exported complete; in CSV every field found becomes a column, ACS fields first and then `ext` fields.
- **Only some fields:** choose **Learn fields** and pick from the list, or type a field name and press Enter. `ext` fields are listed one by one.

### Step B6: Preview, Validate, Export

![The preview: how many events match, and a sample](docs/screenshots/web-03-preview.png)

1. **Preview** shows how many events match and a sample of at most 50 of them. It is a sample, not the export. If the number looks wrong, go back to step B3.
2. **Validate** runs every check an export runs, without exporting. Read it line by line (see [Reading Validate](#reading-validate)). The **Export** button stays off until Validate passes, and changing the search, or waiting more than 15 minutes, turns it off again until you validate once more.
3. **Export:** open the **Export** tab. Keep the format **NDJSON.gz**, or choose **CSV** for a spreadsheet, and choose **Start export**. While it runs, **time left (estimate)** counts down. When the banner says **Complete**, you are done.

![A finished export: Complete, matching Abstract's own total](docs/screenshots/web-05-export-complete.png)

If your range reaches the archive, the progress line first shows the archive job, for example "archive job: 1,200 of 2,700 files". That is normal: the archive part is counted and checked when its job finishes. Archive jobs also appear in Abstract's archive job list under your name.

#### Reading Validate

![Validate: every check, with its status](docs/screenshots/web-04-validate.png)

Every line has a status:

| Status | Meaning | What to do |
|---|---|---|
| **PASS** | The check succeeded. | Nothing. |
| **INFO** | Something you should know, such as the estimated time or how the count was made. | Read it. |
| **WARN** | The export can run, but part of the proof is missing or the result may be partial. | Read the line before you export. Each case is below. |
| **FAIL** | The export cannot run as it is. | Change what the line says, then validate again. |

The lines that matter most:

- **Filter proof** (1): for each filter, the tool searches for a value that cannot exist and expects 0 events; "A value that cannot exist matched 0 events, so the filter is applied" proves it. For other filters the line reads "Removing it changes the count (N vs M), so the filter is applied". A **WARN** here says the filter made no difference in a short sample window, so look at the preview before exporting.
- **Filtered vs unfiltered** (2): the number of events your search matches, against the number with no filter, in a short **sample window** that the line names. These numbers cover only that window, which is why they are smaller than the preview's total.
- **Cross-check:** the same search counted a second, independent way, where it can be.
- **Export plan** (3): how many events, and how many time slices, will be exported; for the archive, how many archive jobs.
- **Estimated time:** from the rates this tool measured: about 700 events a second from recent data with a field list, about 230 with every field, and for the archive about a minute and a half per day of range plus about 4 minutes per archive job. Before an archive job runs, the number of older events is a guess. Busy tenants can be slower.
- **Retention**, **WARN**: the archive cannot be searched with this key, or recent data's limit could not be checked. The export will be **Partial: recent data only**.
- **Nothing matched**, **WARN**: 0 events matched. Check the dataset, fields and filters before you widen the range; the line says whether a second, independent search also counted 0.

## Part 3: Automate with the command line

The command line runs the same search and the same checks as the browser app, with no browser. Use it for scripts and scheduled jobs.

### Step C1: Give the tool your credentials (each terminal window)

In a terminal in the app folder (step B1), set three values. You type the key without it being shown, and it is never saved to a file.

**Mac and Linux:**

```bash
printf 'API key: '; read -rs ABSTRACT_API_KEY; echo; export ABSTRACT_API_KEY
export ABSTRACT_VENDOR_ACCOUNT_ID=AbC123xYz0
export ABSTRACT_EXPECT_TENANT=AbC123xYz0
```

**Windows (PowerShell):**

```powershell
$env:ABSTRACT_API_KEY = [Net.NetworkCredential]::new('', (Read-Host -AsSecureString 'API key')).Password
$env:ABSTRACT_VENDOR_ACCOUNT_ID = "AbC123xYz0"
$env:ABSTRACT_EXPECT_TENANT = "AbC123xYz0"
```

Replace `AbC123xYz0` with your vendor account ID in both lines. `ABSTRACT_EXPECT_TENANT` is a safety check: the tool refuses to run if the key belongs to a different tenant. These values last until you close the terminal window.

#### Exit codes

The export prints the folder it wrote to, then one result line. Its `"exit_code"` tells a script what happened:

| Exit code | Meaning |
|---|---|
| 0 | Complete. Every matching event was written, matching Abstract's own count. |
| 1 | Incomplete. Run `export --resume <folder> --merge` to finish it. |
| 2 | Stopped by a check or an error. The message says why. |
| 3 | **PARTIAL: recent data only.** The result's `verdict` is `PARTIAL`, and it says "Partial: recent data only. Older data was not searched. Not searched: <start> to <end> UTC." Usually the key cannot run archive searches. It is not a complete export of the range you asked for: running it again stays PARTIAL, and a new export of the range is COMPLETE once the archive can be read. |

More `--where` examples, written as in Abstract's search, inside double quotes; the same line works on Mac, Linux and Windows:

```
--where "user_name !contains example.com"
--where "dest_port >= 1024"
--where "action in (Login, Logout)"
--where "user_name startswith svc- or isempty(user_name)"
--where "ipv4_is_in_range(source_ipv4, 10.0.0.0/8)"
```

Every operator works: `==`, `!=`, `in`, `contains`, `has`, `startswith`, `endswith` (and their `!` forms), `matches regex`, `>`, `>=`, `<`, `<=`, `between`, `isempty()`, `isnotempty()`, `and`, `or`, `not(…)` and brackets. Values need no quotes; put single quotes around a value with a space: `--where "user_name !contains 'example corp'"`. On a Mac or Linux, if the terminal answers "event not found", put the whole condition in single quotes instead.

**KQL and plain English.** `kql check "…"` says how a query runs here without running it, and `kql save "…"` saves the result table of a query such as `summarize`. `nl "what you want"` asks Abstract's assistant to write the KQL and shows it; it runs only with `--preview`.

![kql check and kql save](docs/screenshots/cli-kql.png)

**Shortcut:** build the search in the browser app, then on the **Export** tab choose **Run it on a schedule, Copy as command line**. You get the exact command for that search.

### Step C4: Run it on a schedule

Let the tool write the job for you. In the browser app, on the **Export** tab, open **Run it on a schedule**. Choose where it runs, how often and when, then **Generate the job**. On the command line:

```bash
python3 abstract_search.py automate cron --from-saved "My search" --every 1d --at 01:30 --out ~/abstract-job
```

![Generating a scheduled job](docs/screenshots/web-26-automate.png)

The job it writes, for cron, macOS launchd, Linux systemd, Windows Task Scheduler, GitHub Actions or a Docker or Kubernetes job:

- reads the key from your password manager or key vault through `ABSTRACT_API_KEY_COMMAND`, never from a file;
- refuses to run against any other tenant;
- exports back-to-back time windows, so runs never leave a gap or overlap, and resumes its own folder after a failure;
- keeps 30 days of logs;
- posts an alert to the address in `ABX_ALERT_WEBHOOK` when a run fails, when it is **Partial** and when it exports nothing. Alerts go nowhere until you set that address.

Each window ends 10 minutes before the run starts, so late events can arrive. Events that arrive later than that are not in the export; if your sources are slow, run later in the hour.

> [!WARNING]
> **GitHub Actions and container platforms run the export on someone else's computers.** Your events then pass through that service, and the export is stored there until you delete it. Use them only if your organisation allows it; cron, launchd, systemd and Windows Task Scheduler keep everything on your own machine.

The Help topic on scheduled jobs explains each scheduler, and how to set one up by hand.

## Part 4: Change things in Abstract (review first)

The tool can create, change and delete **fieldsets** and **saved views** in your tenant, one at a time or as a bundle of files. Every change shows a review first and happens only when you confirm.

> [!CAUTION]
> **Before you change your tenant**
>
> 1. **Back up first.** Export a bundle of this tenant (`content export`, or **Saved views → Content as code → Export bundle**). It is your only undo: the tool cannot bring back a deleted item, and Abstract has no undo for these changes.
> 2. **A bundle stops at the first change that fails.** Changes before it have already been made. Compare again afterwards; it should report no differences.
> 3. **Items are matched by name.** An item on the tenant with the same name is updated, whoever created it. Check the **Created by** line in the review.
> 4. **Updating a view with the current search replaces its search** under the same name.
> 5. **Tell the people who use these views and fieldsets** before you confirm.

| Change | Who it affects | Can it be undone? | Protect yourself |
|---|---|---|---|
| Create a fieldset | Only you in Abstract, unless you choose to share it | Delete it | None needed |
| Create a saved view | Everyone on the tenant who can open saved views | Delete it | None needed |
| Update a fieldset or view | Everyone who can see it | Only from a backup bundle | Back up first; check **Created by** |
| Delete a fieldset or view | Everyone who can see it; views that use a deleted fieldset lose those columns | Only from a backup bundle | Back up first; read the list of affected views |
| Apply a bundle | Every item in it | Only from a backup bundle | Back up first; leave **Delete what the bundle does not have** off |

The review always says who the change reaches:

| You are | The review says |
|---|---|
| Creating a private fieldset (the default) | "Only you will see this in Abstract. An API key with views permission on this tenant can still read it." |
| Creating a fieldset you chose to share | "Everyone on the tenant will see this." |
| Creating a saved view | "Everyone on the tenant who can open saved views will see this: saved views have no private setting." |
| Updating or deleting anything | "This changes it for everyone who can see it." |

### Fieldsets

![The fieldset builder: fields from a dataset, with how often each is filled](docs/screenshots/web-20-fieldset-builder.png)

On the **Fieldsets** tab, choose **New fieldset** (or pick a fieldset to change it), start from a dataset and choose **Learn its fields** to see how often each field is filled (1). Tick the fields you want and put them in order (2), name it, choose who can use it, and choose **Review and save to Abstract**.

![The review before a change: exactly what will change, and who will see it](docs/screenshots/web-21-review.png)

The review lists exactly what will be created, changed or removed. Nothing happens until you confirm. A review works once and for 10 minutes, and if someone changed the item after your review, the change is refused so you can look again. Deleting a fieldset lists the saved views that use it.

### Saved views

![Saved views: update or delete a view](docs/screenshots/web-22-views-change.png)

On the **Saved views** tab you can save the current search as a view, with its time range and columns, or rename, update or delete a view. Each one opens the same review.

### Views and fieldsets as files (bundles)

**Saved views → Content as code** writes the tenant's views and fieldsets as a bundle: one small JSON file per item, plus a `bundle.json` that records where they came from. Use it to back them up, keep their history in git, see what changed, or copy them to another tenant.

1. **Export a bundle:** choose views and fieldsets, views only or fieldsets only, then **Export bundle**. The browser saves the bundle, and the same files are written to `content/` in your exports folder.
2. **Load a bundle** into the tenant you are connected to, then **Compare** to see, item by item, what is the same, changed, new or only on the tenant.

   ![Comparing a bundle with the tenant, item by item](docs/screenshots/web-24-content-as-code.png)

3. **Review the changes** opens the **Review the bundle** dialog, which lists every create and update in order; nothing happens until you confirm. **Delete what the bundle does not have** is off by default. Turned on, it deletes, for everyone, the views or fieldsets the bundle does not hold, but only for a kind the bundle holds in full; a bundle of views only never deletes a fieldset. The review shows every delete in red first.

   ![Reviewing a bundle: every delete shown in red before anything happens](docs/screenshots/web-25-bundle-review.png)

### On the command line

`fieldsets create`, `update` and `delete`, `views save`, `update` and `delete`, and `content apply` first show exactly what they would change, then stop. Run the same command again with `--yes` to make the change.

```bash
python3 abstract_search.py content export ~/content/backup         # back up every view and fieldset first
python3 abstract_search.py content diff ~/content/standard         # what a bundle would change here
python3 abstract_search.py content apply ~/content/standard        # the review; add --yes to apply
```

![A change shown on the command line before it is made](docs/screenshots/cli-fieldsets.png)

## Part 5: Other places to run it

### The guided terminal

On a server, or over SSH, start the tool with no options. It takes you through the same steps inside the terminal, using the arrow keys:

**Mac and Linux:** `python3 abstract_search.py` · **Windows:** `py abstract_search.py`

![The guided terminal](docs/screenshots/term-01-start.png)

Press **m** for the menu and **q** to quit. To start, you can also choose **Describe it in plain English** or **Write a KQL query**; the main menu has **Fieldsets in Abstract** and every other tool.

### An AI assistant (MCP)

`abstract_search.py mcp` lets an AI assistant on your computer, such as a desktop assistant or GitHub Copilot in VS Code, run searches, checks and exports through this tool. The key stays in the tool's environment; the assistant never sees it. To add the tool to your assistant, give it this command, with your credentials in its environment (the Help topic on AI assistants has the exact settings for each one):

```json
{"command": "python3", "args": ["/path/to/app/abstract_search.py", "mcp"],
 "env": {"ABSTRACT_VENDOR_ACCOUNT_ID": "AbC123xYz0", "ABSTRACT_EXPECT_TENANT": "AbC123xYz0",
         "ABSTRACT_API_KEY_COMMAND": "op read \"op://Security/Abstract API/credential\""}}
```

Then ask, for example: "Check this KQL against my tenant and tell me how many events it matches in the last 24 hours."

- **It is read-only by default.** It can plan a change to a fieldset or view and show it to you, but it cannot make the change unless the tool is started with `--allow-writes` (or `ABSTRACT_MCP_ALLOW_WRITES=1`).
- **With writes allowed,** the assistant is told to show you each change and wait for your yes, but the tool cannot check that you said it. Keep writes off unless you need them, and use a read-only key (step S2).
- **What it sees:** events the assistant asks to see are sent to the assistant, and from there to its provider. Use it under your organisation's policy for AI tools. `ABSTRACT_MCP_MAX_ROWS` limits how many rows one preview hands to the assistant: 50 unless you set it, and never more than 500.

### Docker

With Docker Desktop running, the computer needs nothing else: no Python and nothing installed.

1. Open a terminal in the `app` folder.
2. Run `./run-docker.sh` on Mac or Linux, or `.\run-docker.ps1` in Windows PowerShell.
3. The first run builds the image, which takes about a minute. The script then prints a link and opens it in your browser.
4. Connect in the page with your vendor account ID and API key, exactly as in [Step B2](#step-b2-connect-and-check-the-tenant).

Your exports are written to `AbstractExports` in your home folder, the same place as without Docker. The link works once: run the script again with `link` for a new one, and with `stop` to stop the app. `./run-docker.sh terminal` opens the guided terminal instead, and `./run-docker.sh datasets` runs one command.

The app in the container can be reached from this computer only, runs without privileges, and can write to your exports folder and nowhere else. Compose, another port and scheduled exports are in the **Run it in Docker** help topic.

### GitHub Codespaces or a dev container

The kit includes a hidden `.devcontainer` folder (Python 3.12, nothing else installed, port 8765 forwarded for the browser app), for VS Code dev containers and GitHub Codespaces.

- **On your own machine:** open the kit folder in VS Code and choose **Reopen in Container**. Give it the key through `ABSTRACT_API_KEY_COMMAND` or type it when asked.
- **GitHub Codespaces:** put the kit in a private repository and add `ABSTRACT_API_KEY`, `ABSTRACT_VENDOR_ACCOUNT_ID` and `ABSTRACT_EXPECT_TENANT` as Codespaces secrets for it. Never put a key in `devcontainer.json`, a `.env` file or the repository.

Then, in the container's terminal, in the `app` folder, run `python3 abstract_search.py --menu` for the guided terminal, or `python3 abstract_search.py --web --port 8765 --no-browser` for the browser app (open it from VS Code desktop, which forwards the port to your computer).

> [!WARNING]
> In a codespace, the tool and your exports run on GitHub's computers, and the exports stay in GitHub's cloud until you delete them or the codespace.

### Settings

You need no settings to get started. Use these only when you need them.

| Setting | What it does | Example value |
|---|---|---|
| `ABSTRACT_VENDOR_ACCOUNT_ID` | Your vendor account ID. | `AbC123xYz0` |
| `ABSTRACT_API_KEY` | Your API key (step C1). | |
| `ABSTRACT_API_KEY_COMMAND` | A command that prints your API key from a password manager or key vault. | `op read "op://Security/Abstract API/credential"` |
| `ABSTRACT_API_KEY_FILE` | A file that holds your API key on one line, where a server mounts secrets as files. | `/run/secrets/abstract_api_key` |
| `ABSTRACT_EXPECT_TENANT` | Refuse to run against any other tenant. Needed for the command line. | `AbC123xYz0` |
| `ABSTRACT_BASE_URL` | Only if Abstract gave you a different API address. | `https://api.abstractsecurity.app` |
| `ABX_OUT_ROOT` | Save exports somewhere other than `AbstractExports` in your home folder. | `~/Evidence` or `D:\Evidence` |
| `HTTPS_PROXY` | Your company's web proxy. | `http://proxy.example.com:8080` |
| `SSL_CERT_FILE` | Your company's certificate file, if your company inspects HTTPS traffic. | `/path/to/company-ca.pem` |

To set one for the current terminal window: `export ABX_OUT_ROOT=~/Evidence` on Mac and Linux, or `$env:ABX_OUT_ROOT = "D:\Evidence"` in PowerShell. To keep it, add the `export` line to `~/.zshrc` (Mac) or `~/.bashrc` (Linux), or on Windows run `setx ABX_OUT_ROOT "D:\Evidence"` once and open a new window. Do this for ordinary settings only, never for `ABSTRACT_API_KEY`.

### If something goes wrong

| What you see | What to do |
|---|---|
| `python3: command not found` (Mac, Linux) | Install Python (step S1). |
| `py` is not recognized (Windows) | Install Python from python.org with **Add python.exe to PATH** ticked, then open a new PowerShell window. |
| Your API key was rejected | The key is wrong or has expired. Ask for a new one. |
| `TENANT MISMATCH` | The key belongs to another tenant. Use the right key, or set `ABSTRACT_EXPECT_TENANT` to the vendor account ID you mean. |
| Could not reach the API | Check your internet connection or VPN. On a company network, set `HTTPS_PROXY`. |
| The TLS certificate could not be verified | On a company network, set `SSL_CERT_FILE`. On a Mac with Python from python.org, run **Install Certificates.command** in the Python folder in Applications. |
| No dataset called … | Use the full name, exactly as `datasets` lists it. |
| Nothing matched | Run Validate and read its lines first: check the dataset, the field names and the filters. Then try a longer time range. |
| A filter returns fewer events than you expected | "Not" filters, such as *does not contain*, leave out events where the field is empty. Tick **or has no value** on the filter, or add `or isempty(FIELD)` on the command line. |
| INCOMPLETE | Browser app: **Export history** tab, **Resume**. Command line: `export --resume <folder> --merge`. |
| Partial: recent data only. Older data was not searched. | The message names the range that was not searched. Usually your key cannot run archive searches: ask your Abstract administrator for that permission, then export that range again. |
| "archive job … will be run again" | Part of the archive could not be read. The tool runs the job again by itself; if it keeps happening, resume the export later. |
| "nothing before DATE exists to export" | Your range starts before your tenant's archive retention: Abstract no longer holds that data. Copies made earlier, for example older exports, may still exist. |
| Your key is not allowed to change a fieldset or view (HTTP 403) | The key can read but not change them. Use a key with write permission (step S2). |
| The browser page stops responding | The terminal window was closed. Start the app again (step B1). |
| "something went wrong in the tool itself" | Send the log file the message names to your Abstract contact. |
| **Open the link from the terminal** (in the browser) | The browser app's link works once. Press **Enter** in the terminal window running the app to get a new link, or start the app again (step B1). |

The app's **Help** tab has more detail on every message. Every error the tool shows, and every call to Abstract's API that failed, is also written to `logs/abstract-search-YYYY-MM-DD.log` in your exports folder; error messages end with "kept in the log: …" and name the file. Logs older than 30 days are deleted. When you ask for help, send the log, plus `run.log` and `manifest.json` for an export. They never contain your API key, but they do contain your search, so share them only with people allowed to see it.

### Where copies of your data end up

Every export makes copies of your data outside Abstract. Know where they are, and delete them when you are done.

| Where | What it holds | Removed by **Delete** on the Export history tab? |
|---|---|---|
| The export's folder in your exports folder | Your events, the search, the counts and the API calls made | Yes, the whole folder |
| Your browser's downloads folder, if you chose **Download** | A second copy of the events | No; delete it yourself |
| `content/` in your exports folder | Saved views and fieldsets from a bundle export (searches and columns, no events) | No; delete it yourself |
| `logs/` in your exports folder | Errors, failed API calls and your searches; no events | No; deleted automatically after 30 days |
| A scheduled job's folders | A new export folder each run | No; the job keeps 30 days of logs, but delete old exports yourself |
| The scheduler's own service, if the job runs on GitHub Actions or a container platform | The events of each run, on that service's computers | No; delete them there |

What leaves your computer, by way of running it:

- **Browser app, guided terminal, command line:** calls go only to your Abstract API address.
- **Plain English:** the description you type goes to your tenant's own KQL assistant, through Abstract's API.
- **Alert webhook:** a short JSON message with the job's name, the tenant ID, the time window, the exit code, the log's path and the reason; never your events.
- **AI assistant (MCP):** the events the assistant asks to see go to the assistant and its provider.
- **GitHub Codespaces, GitHub Actions, container platforms:** the tool runs on that service's computers, so your events pass through it.

### Keep your exports safe

Exports contain your log data, and the log files contain your searches. Keep them on an encrypted disk, share them only with people allowed to see that data, and delete them when you are done: **Delete** on the **Export history** tab, or `exports --delete <name>` on the command line.

The tool never saves your API key, and forgets it when it stops. The browser app listens only on your own computer (`127.0.0.1`), and only the page it opened can talk to it. The change log and the daily log are readable only by you.
