# Abstract Search & Export

Search, validate and export every matching event from an Abstract tenant, with proof that the export is complete and a check that each filter is applied.

It is a companion to Abstract's own search. Build a search with filters, write it in KQL, or describe it in plain English; check it; then export a large result in full, straight to your computer. It reads from your tenant. The only things it can change there are fieldsets and saved views, and only after you review each change and confirm it. It does not delete, mask, redact or stop the collection of any data in Abstract, and every export is a new copy of your data outside Abstract.

## What it is for

Use it when you need **every** event that matches a search, as a file you can hand on, and you need to be able to show the file is complete:

- **Investigations and incident response:** pull 7 to 30 days of one user, host or IP from one or more sources, for a timeline or another analysis tool.
- **Audit and legal evidence:** an export with a manifest that records the search, the time range, the checks that ran and the count the platform reported, slice by slice.
- **Hand-off to another team or tool:** CSV for a spreadsheet, NDJSON for a data lake, SIEM or notebook.
- **Scheduled pulls:** the same search every night from the command line, with an exit code a scheduler can act on.
- **Checking a search before you rely on it:** Validate proves each filter narrows the results and counts the search a second, independent way, without exporting anything.
- **Writing the search the way you think:** describe it in plain English and let Abstract's KQL assistant write it, or write KQL with suggestions and a live check of how it will run.
- **Columns and views that stay in Abstract:** build a fieldset from the fields a dataset really fills, and save any search as a saved view, each after a review of exactly what will change.
- **From an AI assistant:** let an assistant on your computer run the same steps through MCP, with the same checks (see [Use it from an AI assistant](#use-it-from-an-ai-assistant)).

It is not a replacement for Abstract's search screens, dashboards or detections.

## What you need

1. **Python 3.8 or newer.**
   - macOS: run `python3 --version` in Terminal to check. If macOS offers to install the Command Line Tools, accept, or install Python from [python.org](https://www.python.org/downloads/).

## Looking after your data

- **Exports contain your log data.** Treat every export folder as you treat the logs themselves: they can hold user names, IP addresses, URLs and message text. Keep them on an encrypted disk, share them only with people allowed to see that data, and delete them when you are done (Exports, Delete; or `exports --delete NAME`).
- **Sharing the kit is safe; sharing exports is a decision.** The kit holds no tenant data, no keys and no settings. Exports, `manifest.json`, `search.json` and saved searches describe your tenant and your searches: share them deliberately.
- **Never paste a key into a chat, ticket or file.** See [Where the API key comes from](#where-the-api-key-comes-from).
- **Know which tenant you are on.** The header always shows the tenant name and ID. The command line refuses to run unless `ABSTRACT_EXPECT_TENANT` matches the key's tenant.
- **Big exports take time and disk.** A day of a busy source can be millions of events. Validate first: it shows the count and the plan before anything is written. See [Large exports](docs/EXPORTS.md#large-exports).
- **Keep exports out of source control.** If you run the tool inside a repository or a dev container, set `ABX_OUT_ROOT` to a folder that is not committed.
- **A zero is a claim.** "Nothing matched" is reported only after a second, independent check; widen the time range before you report that something did not happen.

- **Logs contain your searches, never your key.** Errors and failed API calls go to `logs/abstract-search-YYYY-MM-DD.log` in your exports folder (kept 30 days); each export has its own `run.log`. Send them to your Abstract contact when you need help.
- **Changes to your tenant are reviewed first.** Creating, changing or deleting a fieldset or saved view always shows exactly what will change before anything happens, and each one is recorded in `logs/changes-YYYY-MM-DD.log`.

Every call the tool makes and everything it stores: [Security](docs/SECURITY.md).

## Configuration

Nothing needs configuring to use the browser app: you type the vendor account ID and key when you connect. Everything below is optional, or for the command line and scheduled jobs.

### Where the API key comes from

The key is never written to disk, to a log, to an export, to a saved search or to browser storage. While the tool runs, it holds the key in its own memory, because every search must carry it, and it forgets it when you disconnect or the tool stops. You choose where the key comes from:

| Where the key comes from | How | When to use it |
|---|---|---|
| **Your secret manager, key vault or keychain** (recommended) | Set `ABSTRACT_API_KEY_COMMAND` to a command that prints the key. The tool runs it once when it connects (without a shell) and never logs or stores its output. | Every day: the key exists only in your vault and in the tool's memory while it runs. |
| An environment variable | `ABSTRACT_API_KEY`, set for the session (see [The command line](#the-command-line)). The tool removes it from its own environment as soon as it has read it. | Scheduled jobs, where the scheduler or CI injects the secret. |
| Typed in | The browser app's Connect dialog, or the terminal's hidden prompt. | Occasional use. In the browser the key passes through the page once and is not kept there. |

Examples of `ABSTRACT_API_KEY_COMMAND` (use the names from your own vault):

```bash
export ABSTRACT_API_KEY_COMMAND='op read "op://Security/Abstract API/credential"'                                       # 1Password
export ABSTRACT_API_KEY_COMMAND='az keyvault secret show --vault-name my-vault --name abstract-api-key --query value -o tsv' # Azure Key Vault
export ABSTRACT_API_KEY_COMMAND='aws secretsmanager get-secret-value --secret-id abstract/api-key --query SecretString --output text' # AWS Secrets Manager
export ABSTRACT_API_KEY_COMMAND='gcloud secrets versions access latest --secret=abstract-api-key'                       # Google Secret Manager
export ABSTRACT_API_KEY_COMMAND='vault kv get -field=api_key secret/abstract'                                           # HashiCorp Vault
export ABSTRACT_API_KEY_COMMAND='security find-generic-password -s abstract-api -a api-key -w'                          # macOS Keychain
```

On Windows PowerShell with the SecretManagement module: `$env:ABSTRACT_API_KEY_COMMAND = 'pwsh -NoProfile -Command (Get-Secret -Name AbstractApiKey -AsPlainText)'`.

The command must print the key on one line and nothing else. If it fails, the tool says so without showing its output. With the key from the environment or a command, the browser app connects on its own, so the key never passes through the browser at all.

### Settings

Every setting is an environment variable, read when the tool starts. Nothing is saved between runs.

| Setting | What it does | Default |
|---|---|---|
| `ABSTRACT_VENDOR_ACCOUNT_ID` | Your vendor account ID, so you are not asked for it. | Asked when you connect |
| `ABSTRACT_API_KEY` | The API key, for scheduled jobs. | Asked when you connect |

### Network, proxy and TLS

- **A corporate proxy:** set `HTTPS_PROXY`, for example `HTTPS_PROXY=http://proxy.example.com:8080`.
- **TLS inspection:** set `SSL_CERT_FILE` to your company's CA bundle. On macOS with Python from python.org, run **Install Certificates.command** in the Python folder in Applications once.
- **Over SSH, with no browser here:** start the browser app with `--no-browser` and forward the port from your own computer (`ssh -L 8765:127.0.0.1:8765 <server>`), or use the guided terminal.

### 2. Build the search

The search panel on the left has three tabs: **Builder**, **KQL** and **Plain English**. All three make the same search, checked against your tenant before anything runs.

![Dataset, filter, time range and fields](docs/screenshots/web-02-build.png)

- **Dataset:** start typing and pick from the suggestions.
- **Filters:** **+ Add filter**, pick a field, a condition and the values. Every condition Abstract offers for the field's type is listed: *is one of*, *contains*, *starts with*, *ends with*, *has the word*, patterns, number ranges, subnets and their "not" forms. **Match case** matches upper and lower case exactly; **or has no value** keeps events where a "not" filter's field is empty. With more than one filter, **With more than one filter** chooses **Every filter must match** or **At least one filter must match**. A search from Abstract that mixes `and` and `or` adds **At least one of** lines.
- **Time range:** a preset, or a custom UTC start and end with date and time pickers and quick ranges (Today, Yesterday, Last 7 days, Last 30 days, Last month).
- **Where to search:** **Automatic (recommended)**, which also reads the archive for anything older than recent data, or **Recent data only**.
- **Fields to export:** **Learn fields** shows which fields the dataset uses; **Use suggested fields** picks the useful ones; **Every field of every event** exports complete events.
- **Saved searches** keep a search to reload later.

The **Fields** tab shows the fields a dataset populates and how often each has a value.

## The command line

Set the credentials in the environment, never in a script:

```bash
printf 'API key: '; read -rs ABSTRACT_API_KEY; echo; export ABSTRACT_API_KEY   # the key is not echoed
export ABSTRACT_VENDOR_ACCOUNT_ID=<your vendor account id>
export ABSTRACT_EXPECT_TENANT=<the same id>               # refuses to run against any other tenant
```

Then, in the `app` folder, run the same steps as the browser app:

```bash
python3 abstract_search.py capabilities
python3 abstract_search.py datasets
python3 abstract_search.py preview  --dataset "Okta" --where event.outcome=failure --last 24h
python3 abstract_search.py validate --dataset "Okta" --where event.outcome=failure --last 24h
python3 abstract_search.py export   --dataset "Okta" --where event.outcome=failure --last 24h --merge
python3 abstract_search.py preview  --dataset "Okta" --where "user_name !contains example.com" --last 24h
```

KQL, plain English, fieldsets and saved views:

```bash
python3 abstract_search.py kql check 'events | where data_stream.dataset =~ "Okta" and event.outcome == "failure"'
python3 abstract_search.py export --kql 'events | where data_stream.dataset =~ "Okta" and event.outcome == "failure"' --last 24h --merge
python3 abstract_search.py nl "failed Okta sign-ins" --preview --last 24h
python3 abstract_search.py fieldsets create --name "Okta triage" --from-dataset "Okta"          # shows the change; add --yes to make it
```

`--where` takes a field and values, or any condition written as in Abstract's search, in double quotes. Every command prints each call it makes to Abstract's API to standard error as it happens, the key masked as `********`; `--hide-api` turns it off.

## How an export is proven complete

1. **Plan.** The range is cut into time slices that each fit in one answer from the platform.
2. **Prove the filters.** Each filter is tested on your tenant before anything is exported. A filter that cannot be confirmed stops the export or is reported as a warning.
3. **Export slice by slice.** A slice is accepted only when the events written match the platform's own count for that slice. A slice that does not reconcile is retried or split, and the export is reported INCOMPLETE rather than finishing short.
4. **Write each event once.** Duplicate copies of the same event are written once and counted in `stored_duplicates`.
5. **Combine.** The slice files are combined into one `export.<format>` only after every slice is complete.

Everything is recorded in `manifest.json` in the export folder, and every step and API call in `run.log` beside it. An INCOMPLETE export resumes from the first unfinished slice. Details, sizes and speeds: [Exports](docs/EXPORTS.md).

## Views and fieldsets as code

Back up, compare, version and copy saved views and fieldsets as plain JSON files, one per item, with a `bundle.json` that records the source tenant and a SHA-256 for every file. Typical uses: a standard set of views for every new customer, the same content across many tenants, a git history of who changed what, and a restore after someone deletes a view. Items are matched by name, never by id, so bundles move between tenants. Applying is one review for the whole bundle: fieldsets first, then views, then any deletes, each re-read just before it is changed, stopping at the first failure with a report of what was done. Deleting what a bundle does not have is off unless you ask, and then only touches a kind the bundle holds in full.

```bash
python3 abstract_search.py content export ~/content/my-tenant          # every view and fieldset
python3 abstract_search.py content diff ~/content/my-tenant             # what differs from the tenant you are connected to
python3 abstract_search.py content apply ~/content/my-tenant            # the review; add --yes to apply
```

In the browser app: **Saved views → Content as code**. Details: [docs/CONTENT-AS-CODE.md](docs/CONTENT-AS-CODE.md).

## Run it on a schedule

`automate` writes a ready job for cron, macOS launchd, Linux systemd, Windows Task Scheduler, GitHub Actions, or a Docker or Kubernetes CronJob. Every job reads the key from a secret store, never a file; checks the tenant; exports back-to-back windows so runs never leave a gap or overlap; resumes its own folder after a failure; treats exit codes 0 and 3 as success; keeps 30 days of logs; and posts a JSON alert to `ABX_ALERT_WEBHOOK` when a run fails.

```bash
python3 abstract_search.py automate github-actions --from-saved "Okta failures" --every 1h --out ./job
```

In the browser app: **Export → Run it on a schedule**. Details: [docs/AUTOMATION.md](docs/AUTOMATION.md).

## Use it from an AI assistant

`python3 abstract_search.py mcp` runs the tool as an MCP server, so an AI assistant on your computer (a desktop assistant, GitHub Copilot in VS Code, Cursor and other MCP clients) can use the same steps: see what your tenant supports, check and run KQL, turn a question into KQL, preview, validate and export, and plan changes to fieldsets and saved views. The key stays in the tool's environment and is never sent to the assistant. The server is read-only unless it is started with `--allow-writes` (or `ABSTRACT_MCP_ALLOW_WRITES=1`); with writes allowed, the assistant is told to show you each change and wait for your yes, but the tool cannot check that you said it. Events the assistant asks to see go to the assistant and its provider. `ABSTRACT_MCP_MAX_ROWS` caps the rows one preview returns (50 by default, at most 500). Setup for each client: [Use the tool from an AI assistant](docs/MCP.md).

## Verifying, upgrading and uninstalling

**Verify the download.** The kit comes as `abstract-search-export-0.5.0.zip`, with `abstract-search-export-0.5.0.zip.sha256` next to it. Check the zip before you unzip it:

```bash
shasum -a 256 -c abstract-search-export-0.5.0.zip.sha256      # macOS
sha256sum -c abstract-search-export-0.5.0.zip.sha256          # Linux
```

In PowerShell, `(Get-FileHash .\abstract-search-export-0.5.0.zip).Hash -eq (Get-Content .\abstract-search-export-0.5.0.zip.sha256).Split(' ')[0]` prints `True` when the file is intact. `python3 abstract_search.py --version` prints the version and the kit's build record; quote it when you ask for help.

**Upgrade.** Unzip the new version into a new folder and delete the old one when you are happy. Your exports folder is separate, so saved searches carry across, and an unfinished export from an earlier version can be resumed by the new one.

**Uninstall.** Delete the kit folder and the exports folder (`~/AbstractExports`, or your `ABX_OUT_ROOT`), after keeping any exports you need. Remove any scheduled job you set up. The tool writes nothing else.
